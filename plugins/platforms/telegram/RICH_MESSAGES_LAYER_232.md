# Telegram Rich Messages and Inline Buttons (MTProto layer 232)

This is the implementation reference for Hermes's Telegram RichMessage path. It covers the exact layer-232 Telethon TL constructors used by the adapter, the richer constructors that the layer-232 schema makes available, the Hermes conversion helpers, button forms, and local limits.

## Protocol and version

Hermes uses **Telethon v1.45.0** from the pinned Codeberg source revision `9a02e4746f330b9886dd4e63472b9ed23b01a9d1`. That project-pinned source declares **MTProto layer 232**. The upstream PyPI distribution with the same version string is older (layer 229); the version number alone does not identify Hermes's schema. `plugins/platforms/telegram/transport_policy.py` enforces the version, while `plugins/platforms/telegram/TRANSPORT_CHANGES.md` records the source revision and layer distinction. This reference is for the pinned v1 client; Telethon v2 is not part of this contract.

The TL classes below are generated by Telethon. They are not Hermes dataclasses or enums. Hermes owns the conversion/request helper functions described below; Telethon's generated schema owns constructor names, field types, serialization, and protocol compatibility.

## The three button surfaces are different

Do not conflate these structures:

1. **RichText inline control:** `TextButton(text, type, style)` is a node inside a `TypeRichText` tree, usually nested in `TextConcat`. It is part of the RichMessage body.
2. **RichMessage block button:** `PageButton(text, type, style)` is grouped in a `PageBlockButtonRow(buttons, ...)` inside `InputRichMessage.blocks`. It is also part of the rich body, but is block-level rather than inline text.
3. **Ordinary inline keyboard:** `ReplyInlineMarkup(rows)` contains `KeyboardInlineButtonRow(buttons)`, whose `KeyboardInlineButton(text, type, style)` objects are attached as `reply_markup` on a message request. It is not a RichText node or a page block.

A regular reply keyboard is a fourth, separate UI: `ReplyKeyboardMarkup` → `KeyboardButtonRow` → `KeyboardButton`. It sends button text as a message; it is neither an inline callback keyboard nor part of the RichMessage body. `ReplyKeyboardHide` removes it.

## In-body buttons in Rich HTML (Bot API 10.3)

Bot API 10.3 added buttons inside the message body. In the Rich HTML form they are written as `<tg-button>` elements, grouped in `<tg-button-row>` rows, and parsed by the server from the `InputRichMessageHTML` string. They render as the pill buttons clients show for rich messages, woven into headings, tables, foldouts, and paragraphs. This is the form the `/start` welcome and the `/settings` pages use, and the form the agent tool renders for HTML bodies. It is distinct from surfaces 1–2 above: no `TextButton`/`PageButton` TL nodes are built for these cards.

Syntax (from the Bot API reference):

```html
<tg-button-row align="center">
  <tg-button type="url" style="primary" url="https://t.me">url</tg-button>
  <tg-button type="callback_data" style="link" data="callback">callback</tg-button>
  <tg-button type="copy_text" text="...copy">Copy</tg-button>
  <tg-button type="disabled">Disabled</tg-button>
</tg-button-row>
```

Kinds: `url` (http/https/`tg://`; a profile action is a URL button to `tg://user?id=<id>`), `callback_data` (1–64 bytes), `web_app`, `login_url`, `switch_inline_query` variants, `copy_text` (1–256 characters), `disabled`. Styles: `primary`, `success`, `danger`, `link`; `link` is callback-only. Hermes builds these only through `rich_button()`/`rich_button_row()` in `mtproto_rich.py`, which validate label (1–64 characters), callback bytes, copy length, URL scheme, and style rules locally, and deliberately offer no WebView kind: the server rejects WebView buttons live with `ButtonTypeInvalidError`. The agent-facing `rich_message_send` tool exposes only the one-way kinds (`url`, `copy`, `profile`) with optional `primary`/`success`/`danger` styles; callback pills exist only in native UI code where the adapter already routes their payloads. The authoring reference for agents is `skills/messaging/telegram-rich-messages/SKILL.md`.

A `<tg-button>` may sit inline in a paragraph or a table cell, or in a row block. The HTML detector recognizes `tg-button`/`tg-button-row` tags, so auto-format sends containing only buttons still select `InputRichMessageHTML`.

## Hermes helper API

The implementation lives in `mtproto_rich.py` and `rich_blocks.py`.

| Helper | Behavior |
|---|---|
| `input_rich_message(content, *, rich_format="auto")` | Main selector. Accepts `auto`, `markdown`, `html`, or `blocks` (trimmed and lowercased); rejects other values. Enforces the 32,768-character input limit. Returns one of the native input constructors below. |
| `input_rich_markdown(markdown)` | Returns `InputRichMessageMarkdown(markdown=...)`, after page-marker and hard-line-break normalization. |
| `input_rich_html(html)` | Returns `InputRichMessageHTML(html=...)`, after page-marker normalization; this native path does not sanitize to entities or fall back to plain text. |
| `_input_rich_blocks(markdown)` | Internal converter to `InputRichMessage(blocks=...)`; validates the resulting tree and its limits. |
| `send_request(peer, markdown, *, reply_to=None, top_msg_id=None, no_webpage=None, reply_markup=None, rich_format="auto")` | Builds `functions.messages.SendMessageRequest` and puts the native input object in `rich_message`. The ordinary `message` string is also populated because the TL request requires it; it is companion request data, not a separate send or retry fallback. |
| `edit_request(peer, message_id, markdown, *, no_webpage=None, reply_markup=None, rich_format="auto")` | Builds `functions.messages.EditMessageRequest` with `rich_message`; `message_id` is converted to `int`. |
| `guest_result(query_id, markdown, *, reply_markup=None)` | Builds `InputBotInlineResult` containing `InputBotInlineMessageRichMessage(rich_message=..., reply_markup=...)`, wrapped in `SetBotGuestChatResultRequest`. |
| `inline_markup(rows)` | Hermes convenience builder for an ordinary inline keyboard. Each button is `(label, callback_payload, style)`; `style` is `primary`, `success`, `danger`, or `None`. Empty input returns `None`. The helper builds callback buttons with Telethon's `Button.inline` and serializes them as `ReplyInlineMarkup`. |
| `normalize_rich_markdown(markdown)` | Converts lone newlines to Markdown hard breaks while preserving protected constructs such as lists, tables, math and code. |
| `normalize_page_indexation(content, *, rich_format)` | Canonicalizes standalone page-index footers. |
| `rich_button(label, *, kind, value=None, style=None)` | Renders one validated in-body `<tg-button>` pill (`url`, `callback`, `copy`, `profile`, `disabled`); see the Bot API 10.3 section below. |
| `rich_button_row(buttons, *, align=None)` | Groups 1–8 rendered buttons into one `<tg-button-row>` block. |
| `rich_page_footer(page, pages, total)` | Renders the bottom page indexation as one italic HTML paragraph. |
| `split_rich_message(content, max_length=32_768)` | Splits long content on natural boundaries without cutting recognized protected structures; adds `(part/total)` markers. Minimum configured chunk size is 64 characters. |
| `markdown_entities(markdown)` | Compatibility path: parses Markdown to visible text plus validated UTF-16 Telethon entities. It does not create a RichMessage. |
| `send_markdown_entities_request(...)`, `edit_markdown_entities_request(...)` | Build ordinary `SendMessageRequest` / `EditMessageRequest` using entities, not `rich_message`. |
| `detect_rich_format(content)` | Compatibility classifier returning `html`, `markdown`, or `plain`. |
| `text_and_entities(content, rich_format="auto")` | Compatibility path returning visible text and entities. Accepted modes are `auto`, `markdown`, `html`, and `plain`; `blocks` is not accepted here. This is distinct from `input_rich_message`'s format selection. |

### `rich_format` selection

`input_rich_message` selects in this order:

- `html`, or `auto` when recognized rich HTML is detected → `InputRichMessageHTML`.
- `blocks` → explicitly parse Markdown-like content into a native block tree.
- `markdown` → use native blocks when copyable code is found; otherwise use `InputRichMessageMarkdown`.
- `auto` → use blocks when native math or copyable code is detected; otherwise use `InputRichMessageMarkdown`.

The HTML detector recognizes complete supported tags after prose while avoiding HTML-looking examples inside Markdown code spans/fences. A rich-request RPC failure is not retried as an ordinary text message.

## Layer-232 rich payload constructors

### Input and returned message forms

The `TypeInputRichMessage` union has three variants:

- `InputRichMessage(blocks, rtl=None, noautolink=None, photos=None, documents=None, users=None)`
- `InputRichMessageHTML(html, rtl=None, noautolink=None, files=None)`
- `InputRichMessageMarkdown(markdown, rtl=None, noautolink=None, files=None)`

The server-side `TypeRichMessage` variant is `RichMessage(blocks, photos, documents, rtl=None, part=None)`. Do not substitute that result constructor for the input constructors used in send/edit requests.

Rich-file references available to HTML/Markdown input are `InputRichFilePhoto(id, photo)` and `InputRichFileDocument(id, document)`. `InputRichMessage` block payloads can also carry photo/document/user references via its optional lists. The demo intentionally does not fabricate media references.

### Complete `TypeRichText` constructor catalog

RichText objects can be nested. Text wrappers generally take a child `text`; concatenation takes a list of RichText nodes. The layer-232 `TypeRichText` union contains:

- `TextEmpty()`; `TextPlain(text)`; `TextConcat(texts)`.
- Formatting: `TextBold(text)`, `TextItalic(text)`, `TextUnderline(text)`, `TextStrike(text)`, `TextFixed(text)`, `TextMarked(text)`, `TextSpoiler(text)`, `TextSubscript(text)`, `TextSuperscript(text)`.
- Links and semantic text: `TextUrl(text, url, webpage_id)`, `TextEmail(text, email)`, `TextPhone(text, phone)`, `TextMention(text)`, `TextMentionName(text, user_id)`, `TextHashtag(text)`, `TextCashtag(text)`, `TextBotCommand(text)`, `TextAutoUrl(text)`, `TextAutoEmail(text)`, `TextAutoPhone(text)`, `TextBankCard(text)`, `TextTonAddress(text)`.
- Other content: `TextImage(document_id, w, h)`, `TextAnchor(text, name)`, `TextMath(source)`, `TextCustomEmoji(document_id, alt)`, `TextDate(text, date, relative=None, short_time=None, long_time=None, short_date=None, long_date=None, day_of_week=None)`, `TextDiff(text, old_text)`.
- Inline rich control: `TextButton(text, type, style=None)`.

Hermes's Markdown-to-RichText converter uses `TextPlain`, `TextEmpty`, `TextConcat`, formatting/link/semantic nodes listed above when applicable, and `TextMath` for inline TeX. It uses `TextButton` for eligible inline-code copy actions. The complete union list describes what the pinned layer knows; it does not claim Hermes's Markdown parser generates every member.

## Complete `TypePageBlock` constructor catalog

These are the layer-232 block variants in Telethon's `TypePageBlock` union. Most text-taking variants use `TypeRichText`; fields below are the generated constructor fields (optional fields retain their protocol defaults).

- Basic structure: `PageBlockUnsupported()`; `PageBlockTitle(text)`; `PageBlockSubtitle(text)`; `PageBlockAuthorDate(author, published_date=None)`; `PageBlockHeader(text)`; `PageBlockSubheader(text)`; `PageBlockParagraph(text)`; `PageBlockPreformatted(text, language)`; `PageBlockFooter(text)`; `PageBlockDivider()`; `PageBlockAnchor(name)`; `PageBlockKicker(text)`; `PageBlockThinking(text)`.
- Headings: `PageBlockHeading1(text)`, `PageBlockHeading2(text)`, `PageBlockHeading3(text)`, `PageBlockHeading4(text)`, `PageBlockHeading5(text)`, `PageBlockHeading6(text)`.
- Lists and quotes: `PageBlockList(items)`; `PageBlockOrderedList(items, reversed=None, start=None, type=None)`; `PageBlockBlockquote(text, caption, collapsed=None)`; `PageBlockBlockquoteBlocks(blocks, caption)`; `PageBlockPullquote(text, caption)`; `PageBlockDetails(blocks, title, open=None)`.
- Data/math/button blocks: `PageBlockTable(title, rows, bordered=None, striped=None, compact=None)`; `PageBlockMath(source)`; `PageBlockButtonRow(buttons, align_left=None, align_center=None, align_right=None)`.
- Media/layout blocks: `PageBlockPhoto(photo_id, caption, spoiler=None, url=None, webpage_id=None)`; `PageBlockVideo(video_id, caption, autoplay=None, loop=None, spoiler=None)`; `PageBlockAudio(audio_id, caption)`; `PageBlockDocument(document_id, caption)`; `PageBlockCover(cover)`; `PageBlockEmbed(caption, full_width=None, allow_scrolling=None, url=None, html=None, poster_photo_id=None, w=None, h=None)`; `PageBlockEmbedPost(url, webpage_id, author_photo_id, author, date, blocks, caption)`; `PageBlockCollage(items, caption)`; `PageBlockSlideshow(items, caption)`; `PageBlockChannel(channel)`; `PageBlockRelatedArticles(title, articles)`; `PageBlockMap(geo, zoom, w, h, caption)`; `InputPageBlockMap(geo, zoom, w, h, caption)`.

Additional supporting constructors are `PageCaption(text, credit)` and `PageRelatedArticle(url, webpage_id, title=None, description=None, photo_id=None, author=None, published_date=None)`. Lists use `PageListItemText(text, checkbox=None, checked=None)` or `PageListItemBlocks(blocks, checkbox=None, checked=None)`; ordered lists use `PageListOrderedItemText(text, checkbox=None, checked=None, num=None, value=None, type=None)` or `PageListOrderedItemBlocks(blocks, checkbox=None, checked=None, num=None, value=None, type=None)`. A `PageBlockTable.rows` list contains `PageTableRow(cells)`; each cell is `PageTableCell(header=None, align_center=None, align_right=None, valign_middle=None, valign_bottom=None, text=None, colspan=None, rowspan=None)`.

Hermes's current Markdown block converter emits headings, paragraphs, dividers, preformatted code, block quotes, tables, unordered/ordered lists (including nested/task-list forms), `PageBlockMath`, and copy-action button rows. The showcase additionally composes `PageBlockPullquote`, `PageBlockDetails`, `PageBlockFooter`, and button rows by hand. Other constructors in the schema catalog are available TL types, not a promise that the Markdown converter or demo currently builds them.

## Button classes and constructors

### RichText and block-level buttons

Both rich buttons use the common action union and a rich-button style:

- `TextButton(text: TypeRichText, type: TypeInlineButtonType, style: RichButtonStyle | None = None)` — inline in text.
- `PageButton(text: TypeRichText, type: TypeInlineButtonType, style: RichButtonStyle | None = None)` — placed in a `PageBlockButtonRow`.
- `RichButtonStyle(bg_primary=None, bg_danger=None, bg_success=None, link=None)` — optional presentation flags for rich-body buttons.
- `PageBlockButtonRow(buttons, align_left=None, align_center=None, align_right=None)` — groups `PageButton` objects.

### Complete `TypeInlineButtonType` action catalog

Layer 232's generated union includes:

- `InlineButtonTypeUrl(url)`
- `InlineButtonTypeUrlAuth(url, button_id, fwd_text=None)`
- `InputInlineButtonTypeUrlAuth(url, request_write_access=None, fwd_text=None, bot=None)`
- `InlineButtonTypeWebView(url)`
- `InlineButtonTypeCallback(data: bytes, requires_password=None)`
- `InlineButtonTypeGame()`; `InlineButtonTypeBuy()`
- `InlineButtonTypeSwitchInline(query, same_peer=None, peer_types=None)`
- `InlineButtonTypeUserProfile(user_id)`; `InputInlineButtonTypeUserProfile(user_id)`
- `InlineButtonTypeCopy(copy_text)`
- `InlineButtonTypeDisabled()`

Hermes uses `InlineButtonTypeCallback` for callback actions and `InlineButtonTypeCopy` for native copy controls. Callback payloads are bytes in the TL constructor. Telethon's `Button.inline(label, data=..., style=...)` helper constructs an ordinary inline callback keyboard button; it is not a `TextButton` or `PageButton`.

### Ordinary inline keyboard

The generated structure is:

- `ReplyInlineMarkup(rows, force_reply=None)`
- `KeyboardInlineButtonRow(buttons)`
- `KeyboardInlineButton(text, type, style=None)`
- `KeyboardButtonStyle(bg_primary=None, bg_danger=None, bg_success=None, icon=None)`

`mtproto_rich.inline_markup(rows)` accepts rows of `(label, callback_payload, style)` tuples and builds only callback buttons. Its documented style strings are `primary`, `success`, `danger`, or `None`; style values are passed to Telethon for validation. For direct construction, `KeyboardButtonStyle` uses optional `bg_primary`, `bg_success`, and `bg_danger` flags (plus optional `icon`). This keyboard is attached through a request's `reply_markup` field.

### Reply keyboard (not inline)

`ReplyKeyboardMarkup(rows, resize=None, single_use=None, selective=None, persistent=None, force_reply=None, placeholder=None)` contains `KeyboardButtonRow(buttons)`, whose `KeyboardButton(text, type, style=None)` uses the separate `TypeButtonType` union. The reply-keyboard constructors include `ButtonTypeDefault()`, `ButtonTypeRequestPhone()`, `ButtonTypeRequestGeoLocation()`, `ButtonTypeRequestPoll(quiz=None)`, `ButtonTypeRequestPeer(button_id, peer_type, max_quantity)`, `InputButtonTypeRequestPeer(button_id, peer_type, max_quantity, name_requested=None, username_requested=None, photo_requested=None)`, and `ButtonTypeSimpleWebView(url)`. `ReplyKeyboardHide(selective=None)` hides the keyboard; `ReplyKeyboardForceReply(single_use=None, selective=None, placeholder=None)` requests a reply. These are reply-markup alternatives, not inline callback buttons.

## Request signatures and wire path

The layer-232 generated methods expose the relevant fields as follows:

- `functions.messages.SendMessageRequest(peer, message, ..., reply_markup=None, ..., rich_message=None)` — `message` is a required ordinary string; `rich_message` is an optional `TypeInputRichMessage`.
- `functions.messages.EditMessageRequest(peer, id, ..., message=None, media=None, reply_markup=None, ..., rich_message=None)`.
- `types.InputBotInlineMessageRichMessage(rich_message, reply_markup=None)` for an inline bot result.
- `functions.messages.SetBotGuestChatResultRequest(query_id, result)` for the guest-result helper.

Hermes's `send_request`/`edit_request` create those native requests and route them through `TelethonAdapter._mtproto_rich_request`. Their `reply_markup` may be a `ReplyInlineMarkup` or a reply-keyboard markup according to the use case. A RichMessage block tree and request-level keyboard may coexist, but remain separate fields/structures. The button gallery sends the RichMessage with an inline keyboard, then sends a distinct message with a single-use reply keyboard.

## Hermes guardrails and limits

- Rich input is limited to **32,768 characters** (`MAX_RICH_MESSAGE_CHARS`).
- The explicit native-block validator accepts at most **500** counted native block/list-row nodes and at most **16 nested levels** (`MAX_NATIVE_BLOCKS`, `MAX_NESTING_DEPTH`).
- Parsed tables may contain at most **20 columns** (`MAX_TABLE_COLUMNS`).
- Native copy action text is limited by this adapter to **100 characters** (`MAX_CODE_COPY_CHARS`). At 100 characters, inline code can become `TextButton(type=InlineButtonTypeCopy)` and fenced code can produce a `PageBlockButtonRow` with a `PageButton` copy action. At 101 characters, the content remains fixed/preformatted text without a copy action. Agent-tool copy buttons (`rich_message_send`) are limited to **256 characters**, the server's `CopyTextButton` limit; longer values are rejected locally instead of failing with `BUTTON_COPY_TEXT_INVALID`.
- **Live finding (2026-10-27):** the server rejects hand-built `InputRichMessage(blocks=...)` cards for `/plugins` and `/models` with `RICH_MESSAGE_BLOCK_UNSUPPORTED`, including a 14:19 IST plugin-menu payload with no in-body buttons and no table — so buttons/tables are *not* the cause. The block both failing cards shared, and which no working Markdown/HTML-form payload contains, is `PageBlockTitle`: it is an Instant View/article block, absent from the Bot API rich-message block catalog (which uses headings 1–6 instead). Hand-built message cards therefore use `PageBlockHeading1` for their title line, never `PageBlockTitle`. The `/start` welcome (including its profile action, previously a `TextButton` with `InputInlineButtonTypeUserProfile`) and the `/settings` pages were then moved to the Rich HTML form with in-body `<tg-button>` pills, which is the transport the reference showcase uses; live verification of both on the running bot is still pending. The button gallery remains the deliberate blocks-form canary and is left untouched.
- Chunking avoids splitting protected Markdown/HTML structures when it can; one structure too large to fit raises `ValueError` rather than being silently cut.
- Native RichMessage delivery is MTProto-only. The ordinary `message` companion on a send/edit request is not an alternate transport, and there is no Bot API RichMessage fallback.
- Media/collage/slideshow block constructors need real Telegram media references and captions. The `/button` showcase omits fabricated media.
